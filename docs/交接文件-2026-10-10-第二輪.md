### 3.2 ⚠️ `versionCustomContent` 的 `server` 值決定「SDK 登入彈窗」

`x.Module.Login.Control.LoginControl.lua:185-194`：


### 3.3 ⚠️ `_fill_required` 會把 `code` 覆寫成 `1`（失敗）

**這是本輪最隱蔽的 bug，影響所有帶 `code` 欄位的 s2c。**

```python
# 錯誤順序（原本）：
if fields_by_name.get("code"):
    m.code = 0          # ① 先設成功
_fill_required(m)       # ② 後執行 → 對「非 *_id 的整數 required」填保守值 1
                        #    → code 被覆寫成 1（失敗）

# 正確順序（已修）：
_fill_required(m)       # ① 先填
m.code = 0              # ② 最後明確覆寫成 0
```

**症狀**：`login_repeat_s2c`（`1_4`）回 `code=1` → 客戶端印
`[LoginControl] 登入出錯 … #QR系统邏輯錯誤#n` → **連線立即關閉**。

### 3.4 ⚠️ 凡「帶語意的列舉」欄位，不能填保守值 `1`

同一類錯誤的另一個案例：`hero_info_s2c` 的 `type` 被填 `1`，
但客戶端要 `HeroType.Common = 0`（`HeroDefine.lua:14-19`）。

**規則**：`type` / `mode` / `state` / `code` 這類欄位，
**必須回配置表或 Lua 判斷式確認正確值**，`1` 不是安全預設。

### 3.4b ⚠️ 更危險：id 欄位被填充器挑到「別張表的 id」

`_fill_required` 對 id 類欄位會呼叫 `real_id_for()`，挑一個**真實存在**的 id ——
但那可能是**別張配置表**的 id。

**實例（修復 #8，見 §6.8）**：`31_15` 的 `sys_id` 被填成 `1001`，
那是 `DataTable_children` 的角色 id（厄莉希），而客戶端拿它去查
`DataTable_room_object` → 查不到 → `nil.type` → 崩潰 → 卡 85%。

**規則**：**凡是客戶端會拿去查表的 id 欄位，都要寫明確 handler 指定正確的值**，
不要依賴通用填充器。不確定時，先看客戶端的查表函式名（`GetXxxByKey`）
就知道該對應哪張表。

### 3.5 ⚠️ `p_building_center.power_speed` 的 proto 型別是 `int64`

填 `0.0` 會拋 `TypeError: 'float' object cannot be interpreted as an integer`。

**proto 型別對照表**（用 Python 查 `f.type`）：

```
1=DOUBLE   2=FLOAT    3=INT64    4=UINT64   5=INT32
8=BOOL     9=STRING  11=MESSAGE 13=UINT32  14=ENUM
```

### 3.6 ⚠️ `host` 要用 `10.0.2.2`，不要用宿主機區網 IP

實測（2026-10-10）：

```
模擬器 eth0 = 10.0.2.15/24（QEMU user-mode NAT）

ping 10.0.2.2      → ✅ 0% loss (0.19ms)   ← 永遠可達宿主機
ping 192.168.1.100  → ❌ 100% loss          ← 宿主機 WLAN 換 IP 後就死了
```

**`10.0.2.2` 是 QEMU NAT 固定閘道，不受宿主機 WLAN 換 IP 影響。**

## 5. 協定規格

```
C2S: [u16 BE len = 總長-2][u16 BE uniq][u8 sId][u8 mId][body XOR passArr[(uniq+i)&0xFF]]
S2C: [u16 BE len = 總長-2][u8 sId][u8 mId][u8 zflag][body XOR passArr[((sId*16+mId)+i)&0xFF]]
連線建立時客戶端先送裸 2 bytes 01 02 → 必須丟棄，不可回送
zflag != 0 ⇒ body 是 zlib
```

**兩條鐵則**：

1. **`45_6 recharge_new_sync` 只回一次** —— 客戶端收到回應會再送一次，每次都回會變成無限 ping-pong（實測 2773 次/秒 → 全黑）
2. **`26_2 scenario_enter_c2s` 沒有 s2c** —— 它是通知型訊息，不回是對的（見 §6.3）

## 9. 工作模式鐵則（沿用第一輪，仍然有效）

1. **不要修改任何遊戲檔案** —— 不打 Lua 補丁、不改 `lua.ab`、不動 OBB 內容
   （唯一例外：`files/res/UrlList_Android.txt` 的 host，那是必要設定）
2. **不要用「回空清單」繞過問題** —— 和打補丁是同一種錯誤思路
3. **不要猜** —— 每個結論都要有源碼行號或配置表依據
4. **一次一件事** —— 改完先說明，等使用者確認
5. **使用者操作時不要重啟伺服器** —— 會斷他的 TCP 連線
   （本輪踩過：擅自重啟導致 `1_4` 登入失敗，花了額外時間排查）
6. **不要反覆 `pm clear`** —— 會清掉使用者進度

## 10. 對話中學到的溝通要點

- 使用者要的是**結果**，不是過程。報告要**先講結論**，再講證據。
- 每個結論都要附**出處**（檔名:行號 / 配置表 / 日誌時間戳）。
- **不要一次丟大量輸出**（曾把 PowerShell 全量輸出貼出來，使用者體驗很差）。
- 卡住時**誠實說卡住**並要求做一個小實驗，比繼續猜有效。
- 使用者的直覺常是對的（例：他說「可能是 GM 選項沒顯示」，雖然最終不是，但方向是 UI 而非資料）。
